# OpenXJ380 architecture notes

This document records the boundaries that matter for day-to-day maintenance. The
canonical build graph is generated by `tools/gen_ninja.py`; do not use the root
Makefile conventions from older XJ380 snapshots.

## Boot and kernel image

- The UEFI loader is built as `out/BOOTX64.efi` from `boot/`.
- The kernel is linked as `out/kernel.krl` with `ENTRY(KernelMain)` from
  `linker.ld`.
- Normal boot reads `\system\kernel.krl`; installer boot may read
  `\installer\installer-kernel.elf`.
- Built-in kernel, driver, graphics, font, and support objects are linked into
  `out/kernel.krl` and must remain freestanding.

## Driver and module boundary

- `driver/` is for built-in drivers required by the core kernel image.
- `kmod/` is for loadable kernel modules. First-party modules are linked as
  shared `.sys` artifacts and staged under `/mod`.
- Module entry points are named `dlmain`; shared symbols are resolved through
  the kernel dynamic linker.
- Do not move optional module code into `driver/` only to simplify linking.

## Filesystem boundary

- VFS and pseudo-filesystem code lives under `driver/fs/`.
- User-visible syscall behavior is implemented at the syscall boundary in
  `kernel/syscall/sys.cpp` and XAPI wrappers such as
  `kernel/syscall/xapi/xfile.cpp`.
- Retired, fully commented syscall/sysfs source files are intentionally absent;
  `/proc/filesystems` should describe only currently staged filesystems.

## Userland boundary

- User programs link through `user/xapi/` startup and runtime objects.
- Linux compatibility assets and package-manager roots are image-staging inputs,
  not requirements for generating or building `ninja all`.
